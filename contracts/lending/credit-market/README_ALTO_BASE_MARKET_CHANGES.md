# AltoBaseMarket Inheritance Changes

This document records every change made to the audited `AltoBaseMarket` to
support `AltoConvexCreditLine` as a direct market variant. The comparison
baseline is Git commit `66c0a9a71df3aebe98fda08503de56c9aea2c4fb`.

## Scope and conclusion

The Base changes are limited to:

- removal of the liquidation-engine requirement from shared initialization;
- six external administrative functions split into unchanged external wrappers
  and internal virtual implementations;
- two collateral transfers moved into internal virtual custody hooks; and
- `virtual` added to one existing internal function and one existing external
  function.

No Base storage declaration or storage gap was changed. Apart from deliberately
accepting a zero liquidation engine during initialization, Borrow and Mint retain
their authorization, pause/freeze rules, accounting, external-call order, event
order, return values, and runtime checks. Generated bytecode and gas usage change
slightly because the initializer and virtual hook dispatch alter compiled control
flow; this is documented under Verification.

## Initializer change

`__AltoBaseMarket_init` itself is reused by `AltoConvexCreditLine`. Its signature,
modifiers, assignments, events, parent initializers, and statement order remain
unchanged.

The original initialization check required a nonzero liquidation engine. That
check has been removed completely from the shared Base initializer. The
remaining address validation is independent of market type:

```solidity
_initParams.borrowToken == address(0)
    || _initParams.collateralToken == address(0)
    || _initParams.oracle == address(0)
```

The effect by variant is:

| Variant | Zero liquidation engine before | Zero liquidation engine now |
| --- | --- | --- |
| Borrow | Reverts | Accepted |
| Mint | Reverts | Accepted |
| Credit Mint | Not available | Accepted |

All other Base initializer checks are unchanged: the borrow token, collateral
token, and oracle must be nonzero, and `maxLtv` cannot exceed
`MATH_PRECISION`. `__Ownable_init` continues to validate the owner.

The pre-existing conditional around `setMarketOnce` means a market initialized
without an engine does not call address zero:

```solidity
if (liquidationEngine != address(0)) {
    IAltoLiquidationEngine(liquidationEngine).setMarketOnce(address(this));
}
```

The Base initializer still assigns the supplied value and emits
`SetLiquidationEngine`. Any variant initialized without an engine therefore
emits `SetLiquidationEngine(address(0), address(0))`.

`AltoConvexCreditLine` additionally requires the nested Base parameter to contain
a zero liquidation engine, preventing a Credit deployment from silently using
the Base liquidation path. This is a concrete-market rule rather than Base
knowledge of a specific market type.

## Administrative hook extractions

The following external functions retain their exact ABI and `onlyOwner`
modifier. Each wrapper now delegates to a corresponding internal virtual hook:

| External wrapper | Internal hook | Logic preserved in the hook |
| --- | --- | --- |
| `setIrm` | `_setIrm` | optional accrual, event, assignment, and nonzero IRM registration |
| `setOracle` | `_setOracle` | zero-address check, event, and assignment |
| `setMaxLtv` | `_setMaxLtv` | liquidation-engine query, both LTV checks, event, and assignment |
| `setLiquidationEngine` | `_setLiquidationEngine` | zero-address check, event, assignment, and market registration |
| `setFeeRecipient` | `_setFeeRecipient` | protocol-fee query, conditional zero-address check, event, and assignment |
| `setAuthorizedCallback` | `_setAuthorizedCallback` | zero-address check, mapping update, and event |

No check was dropped from a default Base implementation. The external wrapper
runs `onlyOwner` before entering its hook, matching the previous modifier/body
order.

`_setFeeRecipient` calls the new nonvirtual `_updateFeeRecipient` helper for its
final two original statements:

```solidity
emit SetFeeRecipient(feeRecipient, _feeRecipient);
feeRecipient = _feeRecipient;
```

This avoids repeating the event and assignment in variants. The external
`setFeeRecipient` function was previously `virtual`; it is now nonvirtual, and
the customization point is `_setFeeRecipient` instead. This has no ABI effect.

### Existing-market dispatch

`AltoBorrowMarket` overrides none of these new hooks, so every call uses the
unchanged Base implementation.

`AltoMintMarket` previously overrode external `setFeeRecipient`. It now
overrides internal `_setFeeRecipient` with the same Mint-specific validation,
then calls `_updateFeeRecipient`. The inherited external wrapper supplies the
same `onlyOwner` check. Its error type, liquidation-engine query, checks, event,
and assignment order remain unchanged.

### Credit dispatch

The Credit variant uses the hooks as follows:

- `_setIrm` requires a nonzero, different fixed-rate IRM, then calls
  `super._setIrm` for accrual, event emission, assignment, and registration.
- `setOracle` uses the complete Base implementation.
- `_setMaxLtv` validates against `foreclosureLtv` because no liquidation engine
  exists.
- `_setFeeRecipient` requires a nonzero recipient, then calls
  `_updateFeeRecipient`. It cannot call the Base implementation because Base
  queries `liquidationEngine.protocolFeePercentage()`.
- `_setLiquidationEngine` and `_setAuthorizedCallback` revert because those
  features are unsupported.

There is no Base `setBorrowOpeningFee` implementation to extract. Base declares
only the virtual `borrowOpeningFee()` getter; each concrete market owns its fee
storage and setter rules.

## Collateral custody hooks

Two existing transfer statements were extracted without moving their execution
point in the surrounding action:

1. `_receiveCollateral(uint256 assets)` contains the original
   `safeTransferFrom(msg.sender, address(this), assets)` from `_addCollateral`.
2. `_sendCollateral(address receiver, uint256 assets)` contains the original
   `safeTransfer(receiver, assets)` from `_removeCollateral`.

For Borrow and Mint, the default hooks perform the exact original transfers.
The surrounding order remains:

- add collateral: input checks, accounting increase, transfer, event, return;
- remove collateral: input checks, authorization, interest accrual, accounting
  decrease, transfer, optional callback, solvency check, event, return.

The Convex overrides replace only custody: `_receiveCollateral` deposits LP
tokens into Convex, while `_sendCollateral` withdraws them before transferring
to the receiver.

## Virtual-only changes

The following functions received only the `virtual` specifier; their bodies and
modifiers were not edited:

- `_isSolvent`, allowing the Credit variant to use its credit-specific value
  calculation and zero-debt fast path;
- `governanceLiquidate`, allowing the Credit variant to implement foreclosure.

`setPauser`, `accrueInterest`, and `_onPause` were not changed. Credit inherits
the external Base implementations, which already dispatch to its existing
`_accrueInterest` override where applicable.

## Responsibility for a zero liquidation engine

Base now treats the liquidation engine as optional at initialization, but it
does not make every liquidation-engine-dependent operation optional. A concrete
market or its deployer is responsible for either setting an engine before using
those operations or overriding them.

| Base path | Behavior when the engine is zero |
| --- | --- |
| initializer registration | skipped by the existing nonzero conditional |
| `_setMaxLtv` | Base attempts `minLltv()` and reverts because address zero returns no data |
| `_setFeeRecipient` | Base attempts `protocolFeePercentage()` and reverts because address zero returns no data |
| `_liquidate` | Base attempts `prepareLiquidation()` and reverts because address zero returns no data |
| `_setLiquidationEngine` | remains usable with a nonzero engine and registers the market |
| `governanceLiquidate` | does not query the engine and is unaffected |

The Credit variant isolates all three Base dereferences: `_setMaxLtv` validates
against `foreclosureLtv`, `_setFeeRecipient` does not query an engine, and
`_liquidate` reverts as an unsupported operation. It also disables
`_setLiquidationEngine` so its deployment-time zero value cannot later be
changed. Its `governanceLiquidate` override exists for Credit foreclosure
semantics, not because the Base implementation dereferences the engine.

Borrow and Mint may now also be initialized with a zero engine. If they are,
their owner must configure a nonzero engine through `setLiquidationEngine`
before calling `setMaxLtv`, calling `setFeeRecipient`, or using public
liquidation. Normal accounting paths and governance liquidation do not query
the engine. This responsibility is intentionally independent of `MarketType`.

## Resulting Credit initialization and storage

Like Borrow and Mint initialization parameters, `CreditMarketInitParams` now
contains `BaseMarketInitParams baseMarketInitParams`. `AltoConvexCreditLine`
calls `__AltoBaseMarket_init(baseMarketInitParams, MarketType.CREDIT_MINT)` and
then initializes foreclosure LTV, credit account, credit limit, opening fee, and
Convex configuration.

`__UUPSUpgradeable_init` remains a separate Credit call because
`__AltoBaseMarket_init` does not call it. Base initializes Ownable, Auth,
ReentrancyGuard, pausers, common market storage, IRM registration, and common
events.

The nested struct intentionally changes the undeployed Convex initializer tuple
and selector. Credit-specific storage now follows inherited Base storage and
the unchanged 35-slot Base gap. The former 40-slot Credit gap was removed; this
layout change is acceptable only because the Convex Credit Line is undeployed.

The inherited `authorizedCallbacks` and `liquidationEngine` getters return
`false` and address zero. Compared with the deleted handwritten Credit getters,
their ABI mutability is `view` rather than `pure`. Unsupported inherited action
wrappers also retain Base pause/freeze/modifier precedence before reaching the
Credit reverting hooks.

## Verification

Verification on 2026-09-08 used a clean archive of baseline commit
`66c0a9a71df3aebe98fda08503de56c9aea2c4fb` and the same compiler/configuration
as the working tree.

- Base, Borrow, and Mint ABIs are byte-for-byte identical to the baseline.
- Base, Borrow, and Mint method-identifier maps are byte-for-byte identical.
- Their storage layouts are identical by label, slot, offset, packing, and type
  shape, including the 35-slot Base gap. Raw compiler type/AST IDs differ only
  because source AST numbering changed.
- Metadata-stripped deployed runtime size changed from 21,972 to 22,031 bytes
  for Borrow and from 20,720 to 20,779 bytes for Mint: +59 bytes each from
  the inheritance plumbing. Including metadata, Borrow changed from 22,025 to
  22,084 bytes and Mint changed from 20,773 to 20,832 bytes.
- The complete lending suite was run on both the untouched baseline and the
  current implementation. Both runs passed the same 523 tests across 78 suites
  with zero failures and zero skips. Removing the initialization requirement
  did not cause an existing BTT failure.
- `forge build` succeeds. Compiling the Credit contract emits one new
  `unreachable code` warning in OpenZeppelin's `_nonReentrantAfter`: inherited
  `liquidate` has `nonReentrant`, while Credit's `_liquidate` override always
  reverts because public liquidation is unsupported. The postlude is therefore
  correctly unreachable for this variant; the revert also rolls back the
  modifier's preliminary state write. Other compiler warnings are pre-existing
  or outside this focused diff.
- The repository-wide suite ran 1,580 tests: 1,579 passed and the existing
  `DeployDusdUsdcCustomPositionsTest.test_customPositions_exactTicks` test
  failed with `Price slippage check`. Running that test alone against the clean
  baseline produces the same failure and gas result, so it is unrelated to the
  Base changes.
- Targeted `forge lint` and `git diff --check` pass. `forge fmt --check` reports
  only existing formatter differences in untouched Base lines; those lines
  were not reformatted to keep the audited diff narrow.
- The current Convex deployed runtime is 26,170 bytes, which is 1,594 bytes
  above the EIP-170 limit of 24,576 bytes. Direct inheritance currently
  prioritizes shared audited logic over deployable bytecode size; this must be
  resolved before mainnet deployment.

The runtime-bytecode hashes are not identical, so this review does not claim
bytecode equivalence. Source review and matched test results establish that the
legacy state behavior is preserved, while the internal jumps explain the
documented code-size and gas deltas.

Commands used for the final checks:

```sh
forge build
FOUNDRY_PROFILE=market forge test
forge test
forge inspect AltoBaseMarket abi
forge inspect AltoBaseMarket storageLayout
forge inspect AltoBorrowMarket methodIdentifiers
forge inspect AltoBorrowMarket storageLayout
forge inspect AltoMintMarket methodIdentifiers
forge inspect AltoMintMarket storageLayout
forge build --sizes
```
